Pantheon Storage Analysis

A one-command storage audit for Pantheon-hosted WordPress, Drupal, and generic sites.

  • Bash
  • Terminus
  • WP-CLI
  • Drush

The problem

Supporting web publishing on Pantheon, I kept running into the same question: what's actually using all the storage? Answering it meant poking around across dev, test, and live for a site that might be WordPress, Drupal, or neither — and naive shell pipes run against remote hosts kept choking on PHP warnings and broken-pipe errors, so the "quick check" was never quick.

Why I built it

I wanted a repeatable, one-command audit that works regardless of platform and produces a clean, shareable report — instead of ad-hoc SSH spelunking that I'd have to reconstruct from memory every time. Run it, get a breakdown, hand the report to whoever asked.

How it works

  • Platform auto-detection: the script asks terminus site:info --field=framework and routes to WordPress, Drupal, or generic analysis automatically.
  • Platform-specific analysis: it runs inline PHP through terminus remote:wp (WP-CLI) or terminus remote:drush (Drush) to break down the storage that matters — wp-content vs. sites/default/files, the largest plugins or modules, and database size.
  • Defensive shell engineering: command output is captured into arrays instead of streamed through pipes (to dodge broken-pipe errors), PHP warnings are suppressed, and noise is filtered out — the reliability work that makes remote analysis actually dependable.
  • One or all environments: analyze a single environment, or all three with a side-by-side comparison.
  • Multi-format export: results export to JSON, CSV, TXT, HTML, and Markdown, with timestamped filenames — pick the format that fits the audience.

Outcome & what I learned

The tool turns a fiddly, error-prone manual task into a single command that produces a consistent report across platforms. The real lesson was defensive shell engineering against messy remote output — error suppression, array-based processing, and careful output filtering — plus the design challenge of making one script handle three different platforms cleanly without becoming a tangle of special cases.
